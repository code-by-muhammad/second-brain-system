# Declared local security profile

Candidate review revision 14 November 2026; FastMCP is 4.1.8 and no advisory exception is carried. The candidate declares the local FastEmbed provider with reranking disabled, loopback MCP and one static local bearer credential. The server checks this configuration before importing Basic Memory, refuses an installed LiteLLM SDK/proxy, and exposes only the six constrained `brain_*` tools. The client verifies the owned listener and rejects non-local destinations, redirects, ambient proxies and OAuth auth objects before transport use.

The separately authorized wiki compiler intentionally sends its selected, screened packet through the assistant program the maintainer selected: the Codex/OpenAI CLI or, since v0.2.7, the Claude Code CLI (`claude -p`, no tools, no user settings, no MCP servers, file attachments switched off). It is not part of the local-only retrieval claim. This candidate requires an explicitly selected program (a native executable on Windows), records its observed byte hash, contains its process lifetime (a Job on Windows, a process group elsewhere) and limits private output. Selection/hash recording does not authenticate a publisher or qualify the receiving device. Missing native selection makes no model call; there is no shell-shim fallback. [Operational changes and limits](docs/REVIEW-FOLLOWUP-20261102.md) apply before compilation.

## Dependency remediation

The locked profile upgrades filelock to 4.2.4, certifi to 2026.10.23, FastEmbed to 0.9.1 and Pillow to 13.0.0. The original audit reported affected versions of all four. See the [filelock releases](https://github.com/tox-dev/filelock/releases), [certifi release](https://github.com/certifi/python-certifi/releases/tag/2026.10.23) and [Pillow security fixes](https://pillow.readthedocs.io/en/stable/releasenotes/13.0.0.html). Model/vector parity and actual index qualification are separate from successful package resolution.

The transitive `opentelemetry-api` dependency is constrained to 1.45.2 for [GHSA-mf5v-w3w3-f6cg](https://github.com/advisories/GHSA-mf5v-w3w3-f6cg), a quadratic-time `traceparent` parsing denial of service published on 13 November 2026 against 1.45.1 and earlier. The resolver moved `opentelemetry-sdk` to 1.45.2 and `opentelemetry-instrumentation` and `opentelemetry-semantic-conventions` to 0.66b2 with it; no product module imports these packages and no other dependency version changed.

The transitive `joserfc` dependency is constrained to 1.7.7 for [GHSA-9pg5-8c7x-5hfx](https://github.com/advisories/GHSA-9pg5-8c7x-5hfx), which the live advisory database reported against 1.7.5 on 30 October. The selected release checks compact JWS size before splitting attacker-controlled segments. A bounded split-trap regression and valid/wrong-key HS256 controls cover the upstream behavior. This patch changes neither the retained parent SDKs nor the database schema. Audit receipts record their scan time because advisory data can change independently of the lock.

LiteLLM is deliberately excluded with uv's `exclude-dependencies`; uv 0.9.16 or newer is required. Basic Memory 0.23.2 still declares the SDK in its distribution metadata, so generic `pip check` can report that declaration as unsatisfied. This is an explicit product composition decision, not a supported installation of every upstream Basic Memory feature. The server refuses any non-FastEmbed provider or any enabled/invalid reranker, including the second LiteLLM import path through reranking. Package discovery, proxy-entrypoint absence and actual search are tested. Do not reinstall LiteLLM to silence a metadata warning or run upstream proxy/provider entry points from this environment.

## No advisory exception since v0.2.6

Through v0.2.5 the raw dependency audit was affected by **GHSA-vqqp-x5qm-5qp4** in FastMCP 4.0.0b1, and a time-limited, source-bound exception covered it because the product creates no OAuth provider and uses only its owned loopback static-token transport. The [maintainer advisory](https://github.com/PrefectHQ/fastmcp/security/advisories/GHSA-vqqp-x5qm-5qp4) was fixed upstream in FastMCP 4.1.2.

v0.2.6 ships `fastmcp` and `fastmcp-slim` 4.1.8 and removes the exception from all four host profiles. Basic Memory 0.23.2 declares `fastmcp==4.0.0b1`, so the newer version is selected with uv's `override-dependencies`. This is a deliberate composition, like the LiteLLM exclusion above: Basic Memory 0.23.2 is run against a FastMCP release it does not declare. Basic Memory itself, its database and its index code are unchanged, and the MCP SDK version in the lock is unchanged. The regression suite, the import smoke test on every CI platform and real tool calls on a device are the evidence for that combination. A later Basic Memory release that declares a patched FastMCP should replace the override, with its own reviewed and reversible data-migration design.

The host-selected Windows `security-exceptions.json` and the Darwin ARM64/Intel and Linux x64 profile files keep their structure: the exact audited dependency graph, an empty exception list, and `source_sha256` for every protected file (all local `app/*.py` modules, the installer/updater/setup helper, dependency declarations/lock, gate and security-profile regression file). The audit gate rejects any advisory, any malformed or unscanned dependency and any mismatched graph. With no exception to apply it no longer reads the source hashes; a regression test keeps them equal to the shipped files so that any future exception starts from reviewed bytes. A new advisory therefore fails the gate until the dependency is patched or an exception is explicitly reviewed and recorded here. The negative tests for OAuth auth-object refusal, an adversarial 401/metadata advertisement and destination rejection remain.

## Evidence and limits

Package advisories are not proof of exploitation, and passing tests are not proof of absence of every defect. Keep raw audit output and private runtime diagnostics separate from shared notes. Verify the frozen release, current file/body/vector coverage, native lifecycle/upgrade/recovery, each named client and actual device/reboot receipts at their stated scopes. No candidate source declaration, model review or dependency audit establishes physical-device or reboot acceptance. All four architecture-specific native audits and the real service matrix must be retained before candidate promotion.

## Corrective candidate qualification

The v0.2.3 Windows candidate carries the v0.1.9 correction to descendant inspection to read process birth with query-only access before requesting a termination-capable retained handle. Unreadable possible descendants still refuse; no PID-only kill or broader process authority is introduced. Its complete release qualification is pending. Rebind and independently review all four exact-source host profiles and re-run the raw audit before release. Keeping accepted v0.1.7 running is not acceptance of its legacy controller for upgrade/recovery.

Recovery remains sealed to the transaction's original controller checkout; v0.2.3 cannot adopt an outstanding v0.1.8 hold. Parent attribution and exited-parent behavior are unchanged, including the legacy v0.1.7 orphan-containment limit. Elevated or protected possible descendants still cause a refusal when their identity or termination-capable handle cannot be verified. See the retained [descendant-inspection qualification boundaries](docs/RELEASE-v0.2.2.md).
