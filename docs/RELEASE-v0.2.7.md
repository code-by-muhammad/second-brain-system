# v0.2.7 candidate - wiki with Claude or Codex on every platform, role change, Windows update corrections

Status: candidate preparation, 16 November 2026. Exact source/manifest, review, CI/audit and scoped device qualification are recorded on the release page, not here. This note is not publication, deployment or physical-device acceptance.

v0.2.6 made the setup assistant-neutral but left the wiki compiler tied to a native `codex.exe` on Windows. A device whose owner has only Claude, or a Mac, could not build wiki pages. The first Windows update of v0.2.6 on an owner device also showed three faults. This candidate corrects both.

## What changed

1. **Wiki with Claude or Codex.** `wiki configure-model --executable <path>` accepts the `claude` or the `codex` program. The assistant is the selected program's own name; nothing else is stored. Claude is called as `claude -p --output-format json --json-schema <schema> --tools "" --strict-mcp-config --setting-sources "" --disable-slash-commands --no-session-persistence --system-prompt <fixed text>`, with the same prompt and packet on standard input that Codex gets, with `--settings '{"disableAllHooks":true}'`, with `CLAUDE_CODE_DISABLE_ATTACHMENTS=1` in its environment, and without the other `CLAUDE...` variables of the calling environment except the ones that say where it signs in (`CLAUDE_CONFIG_DIR`, `CLAUDE_CODE_OAUTH_TOKEN`, and the three provider switches). Those other variables can load plugins with hooks, and they are inherited whenever the command is started from inside an assistant session. Without that variable Claude Code reads any file named as `@path` in its input and sends it along, even with every tool disabled; a note could have named a private file that way. A canary file confirmed both behaviours on Claude Code 2.1.325. Its one result object goes to a private `model-reply.json` in the batch folder, removed with the other batch files by the existing cleanup; the `structured_output` inside it becomes `output.json` and then passes the unchanged shape, evidence and publication checks. A result that reports an error, or carries no structured output, publishes nothing. Sign-in and usage-limit messages from Claude are recognized as the existing "model authentication/quota requires attention" state, for a Claude run only and only from the program's own error output. For a Codex run, whose log mixes the echoed notes, the model's text and the program's diagnostics, what counts is now decided by position: the echoed input and everything from the model's answer on are left out, and of the remaining lines only those that begin with an error mark count. An echo cut short by the read limit, or a log of another shape, counts nothing and the failure is handled as an ordinary one. In v0.2.6 an echo longer than the part of the log that is read could make note text count. Both programs are started without `NODE_OPTIONS`, which could preload code into a Node-script install. The Codex command also switches off, by name, the features that give the model an image reader, image generation, a browser, computer use, a code runner, goals, a sleep timer, other agents and skill or tool lookup (`view_image` could read a file the model chose), hides the model's reasoning from the log with `hide_agent_reasoning=true`, and gains `-c features.hooks=false`: Codex loaded the user's `hooks.json` even with `--ignore-user-config`, seen as hook warnings in a real run.
2. **Wiki on macOS and Linux.** The two Windows-only refusals are gone. On Windows the model still runs in the existing private Job. Elsewhere it runs in its own process group with the same 480-second deadline and the same output bound of 5,000,000 bytes for each of its two output files (answer and log; Codex writes both into one), both checked about five times a second and once more when the program has ended. The program's end is observed without collecting it (`waitid` on Linux, a kernel event queue on macOS), so its process number cannot pass to an unrelated process before the group is signalled. The whole group is ended when the run finishes, fails, passes a limit, or the worker itself is asked to terminate or loses its terminal (SIGTERM, SIGHUP, Ctrl+C; each is noted and acted on by the run loop, so none can arrive between starting the program and holding its handle), and the worker waits until the group is gone. A worker that is killed outright (SIGKILL, power loss) cannot do that; its model then runs on until it ends by itself. On macOS and Linux the selected path may be the usual install link (for example `~/.local/bin/claude`): the link is followed on every run, and the file it names is hashed and recorded in the batch, so an assistant that updates itself keeps working. Windows keeps refusing linked paths and launchers.
3. **One setup switch.** `setup_device.py --wiki claude|codex` looks for that program in the absolute folders of PATH, in order, and records the first one the selection accepts. On Windows it looks for the `.exe` only, names a linked one by its target, and passes over a link whose target has another name. When the requested program cannot be selected the run ends with a failure status and the earlier selection stays. It calls no model and builds nothing; pages are built only by `brain_cli.py wiki run`.
4. **An installed capture device can become the maintainer.** `setup_device.py --role maintainer` on an installed capture device stops the service, writes `Control.md` naming this device (whole and at once, never over an existing file), sets the role in `device.json` and starts the service. It refuses a linked folder or file on the way to `Control.md`, checks the owner before stopping and again after, refuses when the notes name another device or an update is in progress, and on a failure after the stop it reads the device record back: if the role was already written the change stays complete, otherwise the ownership note it created is withdrawn and the device stays capture. A stop that itself fails or is interrupted is followed by a start attempt, and the message says whether the service is running. Either way it tries to start the service again and prints the start command if that fails. With `--no-service` it refuses on any device whose service has ever run (its state files exist), because a running or starting server keeps the old role. On a device whose service was never registered there is nothing to stop; the change is made and the normal start step registers the service. The owner line in `Control.md` is read exactly as the running service reads it. On rollback it removes only an ownership note that still names this device. The other direction and a handoff between devices remain unsupported.
5. **No second Codex skill copy.** Codex also reads `~/.agents/skills`. The client plan wrote the skill only under `~/.codex/skills`, so a device that already had it under `~/.agents/skills` got a second copy and then failed its own acceptance check. The plan now keeps the existing copy current and creates no other, also when the path under `~/.codex/skills` is a link that leads nowhere.
6. **Service start window.** The supervisor reports readiness on a 20-second cycle and the controller waited 60 seconds, which left a new server about 40 seconds to listen. The first start of a new Python environment on Windows exceeded that once; the update rolled back cleanly and passed on the second attempt. The wait is now 180 seconds.
7. **Start failure reason.** "Startup readiness failed" now carries the type and text of the underlying error, so the updater's refusal line shows the cause. `setup_device.py` reports a failed start of an existing registration as it is, instead of trying to register again and showing that refusal.
8. **Guide.** One new section on the maintainer role and the wiki, the rule to run Windows commands from ordinary PowerShell and not from inside the packaged Claude desktop app, and three new troubleshooting rows.

## Boundaries to review

- **Note text goes to a model provider** only in `wiki run`: to the provider of the selected assistant, under the owner's own sign-in and plan. Setup never starts it. The optional Git sync sends notes to the owner's own remote. Separately, whatever a connected assistant reads through the `brain_` tools (search results, note bodies) becomes part of that chat and goes to that assistant's provider like anything else shown to it; indexing and search themselves run on the device.
- **Claude's isolation rests on its command-line flags** as observed in Claude Code 2.1.325: no tools, no user/project/local settings (so none of the owner's hooks and instruction files), no MCP servers, no saved session, and the environment variable that switches off file attachments. Administrator-managed settings are the exception: Claude Code applies managed policy (a managed settings file, device management, registry or remote policy) regardless of `--setting-sources`, including its hooks, and a managed prompt hook receives the note packet. Second Brain does not detect or override managed policy: it has several sources that cannot all be read from outside, it is installed by whoever administers the device, and the only mode that skips it (`--bare`) also refuses the subscription sign-in most users have. The guide tells owners of company-managed computers to ask their administrator or use Codex. A later CLI that changes those flags fails closed here only if it rejects them; the result is still validated against the notes before publication.
- **The JSON schema is passed to Claude on the command line.** It contains the packet's source paths, which are visible to other processes of the same user while the run lasts.
- **The non-Windows runner** ends the process group it created. A program that moves itself, or something it starts, into another process group or session escapes that and can outlive the run; so does everything when the worker is killed outright. The Windows Job has neither gap.
- **Codex cannot be run with an empty tool list.** It has no such switch, and which tools the model sees depends on the Codex version and model, not only on these flags. The command uses the read-only sandbox with approvals set to never and no web search, and switches off by name every feature known to hand the model a shell, a code runner, an image reader, a browser, computer use, goals, a sleep timer, other agents, plugins or hooks. Asked directly, a Codex 0.159.2 run with exactly this command still listed its agent-collaboration tools, a request for user input, its patch tool and a code runner that answered "code-mode host is disabled"; in two such probes it could not read a canary file it was told to read. That is an observation of one version, not a guarantee. v0.2.6 ran Codex with fewer of these switches. With Claude the tool list is empty, so an owner who wants a model with no tools should select Claude.
- **The current-folder rule.** A selected program inside the folder the command is run from is still refused, except when that folder is the user's home folder or one above it. Without the exception a per-user install such as `~/.local/bin/claude` was refused whenever the command was run from the home folder, which is where a new terminal opens.
- **The role change** edits `device.json` outside the update transaction, with the service stopped. It writes the ownership note first and the device record second. If setup is killed outright between the two, the notes name a device that is still capture and nothing links milestones until the change is finished; the next run of setup says so and `--role maintainer` completes it. Like the first-install ownership step, it inspects `Control.md` and then creates it.

## Known limits

- The wiki was exercised on one Mac against a small disposable set of notes, once with Claude Code 2.1.325 and once with an npm-installed Codex, both started by hand and not by the background service. No Windows or Linux device has built pages with Claude yet.
- A Codex installed through npm on macOS or Linux is a script that needs `node` on the service's PATH. Use Claude, or a native Codex build, if a scheduled run cannot find it.
- The wiki is not scheduled by setup. The owner runs `wiki run` or creates a schedule.
- Changing the timezone of an installed device, turning a maintainer into a capture device, and moving the maintainer between devices are not supported.
- A packaged desktop installer is not part of this release.
- The limits listed in the [v0.2.6 notes](RELEASE-v0.2.6.md) that are not named above still apply.
